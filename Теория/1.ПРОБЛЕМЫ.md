### 🔍 Точная причина: одна строчка в логе
```
[ERROR] Could not transfer artifact org.aspectj:aspectjweaver:jar:1.9.6 
        from/to aliyun-public: Read timed out
```
**Что это значит:**
Maven (система сборки Java) пытался скачать конкретный файл библиотеки `aspectjweaver-1.9.6.jar` с китайского зеркала `maven.aliyun.com`. Соединение установилось, но **сервер перестал отвечать** во время передачи данных. Сработал таймаут → сборка упала.

### 🌐 Почему именно `hotel-service`, а остальные собрались?

| Фактор | Как повлиял |
|--------|-------------|
| **Разный набор зависимостей** | У `hotel-service` в `pom.xml` была прописана библиотека `aspectjweaver`. У других сервисов её не было, или они использовали другие версии. |
| **Кэш Maven** | Когда один сервис успешно скачивает библиотеку, она сохраняется в кэш. Следующие сервисы берут её оттуда мгновенно. `hotel-service` просто **не повезло** — он попал на момент, когда кэш ещё не был заполнен, а сеть «просела». |
| **«Лотерея» сети** | Китайский зеркальный сервер `aliyun.com` из России работает нестабильно: то отвечает за 0.5 сек, то висит 30 сек, то обрывает связь. Сборка — это как бросок монетки: если в момент скачивания канал «дрогнул», всё падает. |

> 🧩 **Простая аналогия:**  
> Ты заказываешь 5 посылок из одного склада. 4 приходят вовремя, а 5-я «зависает» на таможне. Проблема не в тебе и не в посылке, а в том, что **конкретный маршрут в этот момент оказался перегружен**.

### 🛠️ Почему наши фиксы не помогли до конца?

| Что мы чинили | Что это дало | Почему не решило проблему |
|---------------|-------------|---------------------------|
| `DOCKER_BUILDKIT=0` | Починили **DNS** (контейнер стал видеть адреса) | DNS — это как «узнать номер телефона». Но если сам разговор прерывается из-за плохой связи, номер не поможет. |

**Итог:** Мы починили **настройки сети** (DNS, маршрутизацию), но не могли починить **физическую стабильность канала** до внешнего китайского сервера.

###  Почему это происходит в реальности?

1. **География:** Сервер `maven.aliyun.com` находится в Китае. Пакеты идут через множество промежуточных узлов. В РФ часть маршрутов может фильтроваться, замедляться или терять пакеты.

3. **Flaky-зависимости:** Это известный термин. Ошибка воспроизводится не всегда, зависит от времени суток, загрузки сети, маршрутизации провайдера.

## 🟥 ЧАСТЬ 3 — Docker Swarm (главная боль)

### Проблема 3.1 — OOM-killer на ноутбуке
**Что:** Поднять 3 ВМ × 2 ГБ RAM на ASUS Vivobook (16 ГБ) не получалось — система убивала процессы.

**Корень:** Недостаточно RAM для одновременной работы 3 ВМ + хоста + IDE.

**Решение:** **Переезд на workstation Fedora 43** (64 ГБ RAM, 2× Xeon E5-2690 v4).

### Проблема 3.2 — Все ВМ получали одинаковый DHCP IP
**Что:** `vagrant ssh manager01` попадал на worker02 — Vagrant не мог различить ВМ.

**Корень:** Vagrant использовал **дефолтную сеть libvirt** (192.168.121.0/24) для управляющего интерфейса, и все ВМ получали один IP через одинаковый MAC-адрес или гонку DHCP.

**Решение:** Создали **отдельную сеть** `do-h-07-net` (192.168.56.0/24) с **жёстким маппингом MAC→IP** в XML-конфиге libvirt:
```xml
<host mac='52:54:00:11:11:01' name='manager01' ip='192.168.56.10'/>
```
И ходили на ВМ напрямую по этим IP, минуя `vagrant ssh`.

### Проблема 3.3 — Vagrant подключался к user-session libvirt
**Что:** Сеть в system-session, ВМ создавались в user-session — они не видели друг друга.

**Корень:** В `Vagrantfile` не был указан URI подключения к libvirt.

**Решение:** Добавили `libvirt.uri = 'qemu:///system'` в Vagrantfile.

### Проблема 3.4 — Race condition при `vagrant up worker02`
**Что:** При параллельном поднятии последняя ВМ "захватывала" чужое имя.

**Решение:** Поднимали ВМ по одной (`vagrant up manager01`, потом `vagrant up worker01`, потом `vagrant up worker02`).

### Проблема 3.5 — DNS отваливался внутри Docker BuildKit
**Что:** При сборке образов на manager01 BuildKit не мог резолвить `maven.aliyun.com`.

**Корень:** BuildKit запускает каждый шаг RUN в **изолированном network namespace** (сетевом пространстве имён) и **не наследует DNS** хоста.

**Решение (комплексное):**
1. Прописали DNS принудительно в `/etc/resolv.conf` + `chattr +i` (защита от перезаписи)
2. Прописали DNS в `/etc/docker/daemon.json`
3. Создали buildx-builder с `--driver-opt network=host`
4. Для упорно падающих сервисов — `DOCKER_BUILDKIT=0` (legacy builder)
5. **Самое важное:** хак с `/etc/hosts` прямо в Dockerfile:
   ```dockerfile
   RUN echo '163.181.1.176 maven.aliyun.com' >> /etc/hosts
   ```

### Проблема 3.6 — Aliyun mirror катастрофически медленный
**Что:** Maven скачивал зависимости со скоростью **190 байт/сек**, сборка hotel-service длилась 37 минут и падала по таймауту на `aspectjweaver:1.9.6`.

**Корень:** Дорога РФ → Китай была плохой именно в эти дни.

**Решение:** Увеличили `maven.wagon.rto` до 30 минут, прописали 3 IP-адреса Aliyun в `/etc/hosts`. Для hotel-service не помогло — **приняли как непосильное** и продолжили с 7 из 8 сервисов.

### Проблема 3.7 — `docker service logs` зависал навсегда
**Что:** Команда `docker service logs <service>` без флагов **никогда не завершалась** — зависла на 6.5 часов.

**Корень:** По умолчанию `--follow=true` — команда ждёт новых логов вечно.

**Решение:** Использовать `--tail N` + `timeout 5 sudo docker service logs ...` (флаг `--no-follow` в этой версии Docker не поддерживался).

### Проблема 3.8 — Postgres healthcheck не помогал
**Что:** Сервисы Spring Boot падали на старте: `DialectResolutionInfo cannot be null`.

**Корень:** `wait-for-it.sh` проверял **только что порт 5432 открыт**, но Postgres ещё не успевал создать **конкретные базы данных** (loyalty_db, balances_db и т.д.), которые ожидали микросервисы.

**Решение:** Создали БД вручную через `docker exec ... psql -c "CREATE DATABASE ..."`.

### Проблема 3.9 — Имена БД в env-переменных НЕ совпадали с init.sql
**Что:** Loyalty-service подключался к `loyalty_db`, а в init.sql создавалась `balances_db`. Аналогично для booking (нужно `reservations_db`, не `bookings_db`) и report (`statistics_db`, не `reports_db`).

**Корень:** Я (Claude) угадывал имена баз по логике вместо того чтобы посмотреть init.sql.

**Решение:** Прочитали init.sql, увидели реальные имена, переписали env-переменные в compose.

### Проблема 3.10 — Nginx падал при старте: `host not found in upstream`
**Что:** В первой версии `nginx.conf` использовался блок `upstream`, который **резолвит хост при старте**. Поскольку gateway-service запускался позже nginx, тот падал.

**Решение:** Переписали без `upstream`-блоков — использовали runtime DNS:
```nginx
resolver 127.0.0.11 valid=10s;
location /api/ {
    set $gateway_upstream "gateway-service:8087";
    proxy_pass http://$gateway_upstream;
}
```

### Проблема 3.11 — `docker stack deploy` не обновлял env-переменные
**Что:** После правки `docker-compose-swarm.yml` запускали `docker stack deploy`, но env у сервисов оставались **старыми**.

**Корень:** Swarm считал что "по сути ничего не поменялось" и не пересоздавал сервисы.

**Решение:** Полный `docker stack rm app && sleep 30 && docker stack deploy ...` (снос и развёртывание заново).

### Проблема 3.12 — Gateway не находил `SESSION_SERVICE_PORT`
**Что:** Spring Boot падал: `Could not resolve placeholder 'SESSION_SERVICE_PORT'`.

**Корень:** Я (Claude) передал в env только `SESSION_SERVICE_HOST` без `_PORT`-вариантов.

**Решение:** Добавили все `*_PORT` для всех 6 сервисов (SESSION/HOTEL/PAYMENT/LOYALTY/BOOKING/REPORT_SERVICE_PORT).

### Проблема 3.13 — Booking/Report не находили RabbitMQ переменные
**Что:** `Could not resolve placeholder 'RABBIT_MQ_QUEUE_NAME'`.

**Корень:** В application.properties эти переменные пишутся через подчёркивание — `RABBIT_MQ_HOST`, **не** `RABBITMQ_HOST` (как было в моём compose).

**Решение:** Переименовали все переменные в compose: `RABBIT_MQ_HOST`, `RABBIT_MQ_PORT`, `RABBIT_MQ_USER`, `RABBIT_MQ_PASSWORD`, `RABBIT_MQ_QUEUE_NAME`, `RABBIT_MQ_EXCHANGE`.

### Проблема 3.14 — Hotel-service так и не собрался
**Что:** Maven падал на скачивании `aspectjweaver:1.9.6` даже с 30-минутным timeout.

**Решение:** Приняли как **непосильное в текущих условиях интернета**. В отчёте отметить — собрано 7 из 8 сервисов.

### Проблема 3.15 — Booking-service падает из-за отсутствующего hotel-service
**Что:** Booking зависит от hotel-service (через `HOTEL_SERVICE_HOST`), а образа hotel-service нет → booking стартует, но валится при попытке вызвать hotel.

**Решение:** Передали env-переменные-заглушки `HOTEL_SERVICE_HOST=hotel-service`, `HOTEL_SERVICE_PORT=8082` — Spring Boot **стартует**, но runtime-вызовы к hotel будут падать с 502/503. Это ожидаемо.

**Что:** Newman пытался ходить на `localhost:8081`, а у нас в Swarm наружу торчит **только порт 80** через nginx.

**Корень:** Коллекция использует переменные `{{API_HOST}}:{{USERS_PORT}}` и `{{API_HOST}}:{{GATEWAY_PORT}}`, и эти переменные не передавались.

**Решение (в работе):** Адаптировать коллекцию через `sed` под `192.168.56.10:80` + поправить пути в nginx.conf.

### Проблема 3.17 — `ECONNREFUSED 127.0.0.1:8081` при `--env-var "baseUrl=..."`
**Что:** Передача `--env-var "baseUrl=http://192.168.56.10"` не помогла — коллекция игнорирует эту переменную.

**Корень:** Коллекция использует `{{API_HOST}}` и `{{USERS_PORT}}`, а не `{{baseUrl}}`.

**Решение:** Передать правильные имена: `--env-var "API_HOST=http://192.168.56.10" --env-var "USERS_PORT=80" --env-var "GATEWAY_PORT=80"`.

### Проблема 3.18 — Newman не установлен на хосте
**Что:** `sudo: npm: команда не найдена`.

**Решение:** Установили nodejs (через `dnf` пакетный менеджер автоматически предложил установку), потом `sudo npm install -g newman`.

### Проблема 3.19 — Конфиг nginx нельзя обновить inplace
**Что:** При попытке обновить `nginx.conf` через redeploy Swarm выдавал:
```

# Стратегия для AnsibleConsul — учим уроки из DO_H_07

Ты уже **прошёл огонь и воду** в DO_H_07 — теперь это превращается в боевой опыт. Разберу всё подробно.

## Сначала — оценка предложений из документа

### ✅ Хорошие идеи
- **Retry-флаги в Maven** — да, нужны, но **недостаточны**. Ты уже видел: при 190 байт/сек никакие retry не помогут.
- **`mvn dependency:go-offline` + `mvn -o`** — отличная идея. Кэш на хосте → копируем в ВМ → собираем без интернета.
- **Vendor-паттерн (libs/ внутри проекта)** — рабочая идея, но муторно.

### ❌ Что **не сработает** для твоего случая
- **Российские зеркала** — ты их уже использовал в DO_H_07, и они **тоже падали**. Aliyun (китайское) работает лучше большинства "российских".
- **Nexus/Artifactory** — отдельный проект на день. Тебе нужно сдать AnsibleConsul, а не строить infrastructure.

### 🎯 Что **реально решит** проблему

Главный урок DO_H_07: **сборка в ВМ из РФ через интернет = 7 часов и таймауты**. Для AnsibleConsul нам нужно **полностью** убрать сборку из критического пути.

# 🚀 Главная стратегия: «всё что можно — на хосте, в ВМ только готовое»

| ❌ DO_H_07 (как было) | ✅ AnsibleConsul (как надо) |

# Проверь свободное место и RAM
df -h /var/lib/libvirt/images

```

🎯 **Цель:** минимум 30 ГБ свободного места на `/var/lib/libvirt/images` и 16 ГБ свободной RAM.

## Шаг 1 — Поднять локальный кэш Maven на хосте Fedora

Это **главное решение**. Соберём jar-файлы **один раз на хосте** (где у тебя нормальный канал), а в ВМ будем **только копировать готовое**.

```bash
# Установить Java и Maven НА ХОСТЕ (если нет)
sudo dnf install -y java-21-openjdk java-21-openjdk-devel maven

java -version  # должно показать openjdk 21
mvn -version
```

**Один раз** — прогреем Maven-кэш для hotel-service:

```bash
# Допустим у тебя hotel-service в ~/AnsibleConsul/src/services/hotel-service
cd ~/AnsibleConsul/src/services/hotel-service

# Создаём settings.xml с китайским mirror (он самый стабильный для РФ)
mkdir -p ~/.m2
cat > ~/.m2/settings.xml << 'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.0.0">
  <mirrors>
    <mirror>
      <id>aliyun-public</id>
      <mirrorOf>central</mirrorOf>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
    <mirror>
      <id>aliyun-spring</id>
      <mirrorOf>spring-milestones,spring-snapshots</mirrorOf>
      <url>https://maven.aliyun.com/repository/spring</url>
    </mirror>
  </mirrors>
</settings>
EOF

# Прогрев — скачиваем все зависимости в ~/.m2/repository
mvn dependency:go-offline -Dmaven.test.skip=true \
    -Dmaven.wagon.http.retryHandler.count=10 \
    -Dmaven.wagon.rto=300000

# Собираем jar
mvn clean package -Dmaven.test.skip=true -o
ls -la target/*.jar
```

🎯 **Результат:** `target/hotel-service-0.0.1-SNAPSHOT.jar` на хосте + полный кэш в `~/.m2/repository/`.

⏰ **Время:** один раз ~10-30 минут (зависит от канала). После этого все сборки **мгновенные** через `-o`.

## Шаг 2 — Подготовить Vagrant с готовыми артефактами

В Vagrantfile **проброс папок с хоста** в ВМ:

```ruby
# AnsibleConsul/Vagrantfile (фрагмент)
config.vm.synced_folder ".", "/vagrant"
config.vm.synced_folder "~/.m2/repository", "/home/vagrant/.m2/repository", type: "rsync",
    rsync__exclude: [".cache/"]
config.vm.synced_folder "./src", "/home/vagrant/src", type: "rsync"
```

⚠️ **Важно:** в libvirt `synced_folder` работает через rsync (по умолчанию) или **9p/virtio-fs** (быстрее, но капризнее). Используй **rsync** — он стабильнее.

## Шаг 3 — Настроить DNS на ВМ заранее (один раз!)

Проблема DO_H_07: внутри Docker BuildKit отваливался DNS. Для Ansible — DNS будет нужен для `apt install`. Решение — **заранее** прописать стабильные DNS:

```bash
# В Vagrantfile добавить provisioner который настроит DNS:
config.vm.provision "shell", inline: <<-SHELL
  # Стабильные DNS (Cloudflare + Google)
  cat > /etc/systemd/resolved.conf << 'EOF'
[Resolve]
DNS=1.1.1.1 8.8.8.8 77.88.8.8
FallbackDNS=9.9.9.9 1.0.0.1
EOF
  systemctl restart systemd-resolved
SHELL
```

`77.88.8.8` — Yandex DNS, на случай если Cloudflare/Google заблокируют.

## Шаг 4 — Кэш apt-пакетов на хосте

Чтобы `apt install docker.io` в плейбуках Ansible не качал каждый раз:

```bash
# Поднять apt-cacher-ng на хосте
sudo dnf install -y apt-cacher-ng
sudo systemctl enable --now apt-cacher-ng
```

Затем в Vagrantfile в provision:

```bash
echo 'Acquire::http::Proxy "http://192.168.56.1:3142";' > /etc/apt/apt.conf.d/00proxy
```

Теперь все ВМ будут качать пакеты **через кэш на хосте**. Первый раз медленно, потом мгновенно.

## Шаг 5 — Подготовить Docker-образы заранее

Если в плейбуке Ansible есть `docker pull image`, то ВМ полезет в Docker Hub. **Ускоряем:**

```bash
# На хосте Fedora — собери все образы для микросервисов один раз
docker pull postgres:14-alpine
docker pull rabbitmq:3.12-management-alpine
docker pull nginx:1.25-alpine
docker pull consul:1.15
docker pull hashicorp/envoy:v1.27.0
docker pull httpd:alpine
docker pull portainer/portainer-ce:latest

# Сохрани все образы в один tar-файл
docker save \
    postgres:14-alpine \
    rabbitmq:3.12-management-alpine \
    nginx:1.25-alpine \
    consul:1.15 \
    hashicorp/envoy:v1.27.0 \
    httpd:alpine \
    portainer/portainer-ce:latest \
    -o ~/ansible-consul-images.tar

ls -lh ~/ansible-consul-images.tar
```

В Vagrantfile прокинь этот tar в ВМ, и в плейбуке Ansible:

```yaml
- name: Load pre-built docker images
  shell: docker load -i /vagrant/ansible-consul-images.tar
```

⚡ Это **в 10 раз быстрее** чем pull из интернета.

# 📦 Стратегия по частям задания

## Part 1 (Ansible) — главные риски и фиксы

### 🚩 Риск 1: `apt install docker.io` повиснет на медленном канале
**Фикс:** apt-cacher-ng (см. Шаг 4). После первого `vagrant up` все следующие будут моментальные.

### 🚩 Риск 2: 7 микросервисов снова будут собираться внутри ВМ
**Фикс:** **НЕ собирай в ВМ!** В Ansible-плейбуке используй `image: zangievmovsar/do-h-07-*` — у тебя **уже** есть готовые образы в Docker Hub после DO_H_07. Просто `docker compose pull` + `docker compose up`.

```yaml
# roles/application/tasks/main.yml
- name: Copy compose file
  copy:
    src: docker-compose.yml
    dest: /home/vagrant/app/docker-compose.yml

- name: Pull images
  shell: docker compose pull
  args:
    chdir: /home/vagrant/app
  environment:
    DOCKER_BUILDKIT: 0  # legacy builder, надёжнее

- name: Deploy
  shell: docker compose up -d
  args:
    chdir: /home/vagrant/app
```

⚡ Это **сразу** убирает все проблемы со сборкой.

### 🚩 Риск 3: Postman снова не достучится (helo localhost:8081)
**Фикс — заранее:** в Vagrantfile прокинь все нужные порты:

```ruby
config.vm.define "node01" do |node|
  node.vm.network "forwarded_port", guest: 8081, host: 8081
  node.vm.network "forwarded_port", guest: 8087, host: 8087
end
```

Тогда `localhost:8087` на хосте будет работать как-есть, без правки коллекции.

### 🚩 Риск 4: postgres init.sql снова создаст не те БД
**Фикс:** **проверь** init.sql от роли postgres **до** запуска. У тебя должна быть `hotels_db` для роли `install_db` в Part 2.

## Part 2 (Consul) — главные риски и фиксы

### 🚩 Риск 1: hotel-service нужно собрать (тот самый который не собирался в DO_H_07!)
**Фикс — главный пункт:** собери hotel-service на **хосте** через прогретый Maven-кэш (Шаг 1). На ВМ только копируй готовый `.jar`.

```yaml
# roles/install_hotels_service/tasks/main.yml
- name: Copy pre-built JAR
  copy:
    src: ../../../../src/services/hotel-service/target/hotel-service-0.0.1-SNAPSHOT.jar
    dest: /home/vagrant/hotel-service.jar

- name: Install Java only
  apt:
    name: openjdk-21-jdk
    state: present
    update_cache: yes

- name: Run jar
  shell: nohup java -jar /home/vagrant/hotel-service.jar > /var/log/hotel-service.log 2>&1 &
  environment:
    POSTGRES_HOST: "127.0.0.1"
    POSTGRES_PORT: "5432"
    POSTGRES_DB: "hotels_db"
    POSTGRES_USER: "postgres"
    POSTGRES_PASSWORD: "postgres"
```

⚠️ Чек-лист Школы говорит: «`openjdk-21-jdk`» — **проверь у себя в pom.xml** какая Java реально нужна. В DO_H_07 ты использовал Java 11 для сборки и Java 8 для запуска. Если задание требует Java 21, может **придётся апгрейдить pom.xml** (это другая история).

### 🚩 Риск 2: Consul не найдёт интерфейс внутренней сети
**Фикс:** в `consul_server.hcl` и `consul_client.hcl` использовать **готовый IP**, не пытаться "автоопределить":

```hcl
# consul_server.hcl
server = true
bootstrap_expect = 1
data_dir = "/var/consul"
advertise_addr = "192.168.56.10"  # IP в сети Vagrant — ЖЁСТКО прописываем
client_addr = "0.0.0.0"
ui_config {
  enabled = true
}
```

🎯 **Урок DO_H_07:** жёстко прописывать IP лучше, чем угадывать через скрипты.

# 📌 Ответ на твой вопрос: «поможет ли всё это?»

**Да, поможет — но 1+5+7 в комбинации.** Конкретно:

✅ **Maven retry** — мелкая помощь, но недостаточная сама по себе.
✅ **Settings.xml с зеркалом** — да, **обязательно**.
✅ **`mvn -o` offline mode** — **главный** фикс.
✅ **`mvn dependency:go-offline`** — твой друг.
✅ **Vendor libs/** — overkill для учебки, но в Nexus в работе пригодится.
❌ **Nexus** — это другой проект, не делай.

**Главное добавление от меня:** не собирай вообще ничего внутри ВМ. Хост → ВМ только копируй готовое. Это убирает 95% проблем DO_H_07.

Жду — когда будешь готов начать AnsibleConsul, дай знать, какая часть первая. Я расскажу пошагово.
